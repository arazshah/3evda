# نقشه‌ی راه اجرایی 3evda.com

**تاریخ:** 2026-10-02
**سند طراحی:** `docs/superpowers/specs/2026-10-02-photographer-platform-design.md`
**جایگزین:** `docs/superpowers/plans/2026-09-11-phase-0-foundation.md` (مربوط به استک قبلی)

## ۱. روند کار هر فاز

```text
main (همیشه قابل دیپلوی)
  └─► branch فاز ──► commitهای کوچک و تست‌دار ──► push ──► Pull Request به main
                                                          │
                                         GitHub Actions: ci.yml (همه‌ی jobها)
                                                          │ همه سبز؟
                                          ┌─── نه ──► رفع، push دوباره
                                          └─── بله ─► بازبینی و تأیید صاحب پروژه ─► Merge
                                                                                     │
                                                       push به main ─► ci.yml روی main ─► deploy.yml ─► Coolify
```

1. هر فاز روی یک branch جدا از آخرین `main` توسعه داده می‌شود: `phase/<N>-<slug>`، یا در جلسه‌های Claude برنچ تعیین‌شده‌ی همان جلسه.
2. کار با TDD پیش می‌رود: اول تست قرمز، بعد پیاده‌سازی، بعد refactor. پیام commitها از Conventional Commits پیروی می‌کند (`feat:`، `fix:`، `test:`، `ci:`، `docs:`).
3. پایان فاز = یک Pull Request با قالب `.github/pull_request_template.md` که چک‌لیست گیت آن فاز را دارد.
4. **Merge فقط وقتی** همه‌ی jobهای اجباری CI سبز باشند، چک‌لیست گیت تکمیل باشد، و صاحب پروژه تأیید کند. روش merge: *Squash* (یک commit تمیز برای هر فاز روی `main`).
5. بعد از merge، `deploy.yml` دیپلوی را در Coolify اجرا می‌کند و smoke test روی دامنه‌ی واقعی اجرا می‌شود.
6. فاز بعدی فقط بعد از سبز بودن دیپلوی فاز قبلی شروع می‌شود و برنامه‌ی تفصیلی آن در `docs/superpowers/plans/` نوشته و تأیید می‌شود.

### ۱.۱ محافظت از `main` (Branch protection)

- push مستقیم ممنوع است و فقط از طریق PR تغییر می‌کند.
- Status checkهای اجباری (بخش ۲) باید سبز باشند و branch باید با `main` به‌روز باشد.
- force push و حذف branch ممنوع است، و همه‌ی گفت‌وگوهای PR باید resolve شده باشند.

## ۲. CI/CD

### ۲.۱ `ci.yml` — روی هر PR و هر push به `main`

| Job (نام چک اجباری) | کار | از فاز |
|---|---|---|
| `backend` | `uv sync --frozen`، `ruff check`، `ruff format --check`، `mypy`، `manage.py makemigrations --check`، `pytest` با Postgres و Redis (service container)، پوشش تست ≥ ۸۵٪ برای `apps/` | 0 |
| `frontend` | `pnpm install --frozen-lockfile`، `lint`، `typecheck`، `vitest run`، `next build` | 0 |
| `contract` | تولید OpenAPI از Django و کلاینت orval، و شکست در صورت وجود اختلاف با نسخه‌ی commitشده | 1 |
| `e2e` | `docker compose up --build --wait` با همان `docker-compose.yml`، اجرای Playwright (دسکتاپ + موبایل) و axe روی gateway | 0 |
| `security` | gitleaks (کل تاریخچه)، `pip-audit`، `pnpm audit --audit-level high`، Trivy روی ایمیج‌ها (high/critical) | 0 |
| `lighthouse` | Lighthouse CI روی خانه، نمونه‌کار و مقاله: Performance، Accessibility، Best Practices و SEO ≥ ۹۰ | 2 |

- همه‌ی actionها با SHA پین می‌شوند، `permissions: contents: read`، `concurrency` برای لغو اجراهای قدیمی، و `timeout-minutes` روی هر job.
- Artifactهای شکست (trace و screenshot Playwright، گزارش پوشش) آپلود می‌شوند.
- Dependabot هفتگی برای pip/uv، npm، GitHub Actions و Docker فعال است.

### ۲.۲ `deploy.yml` — بعد از سبز شدن `ci.yml` روی `main`

1. وبهوک دیپلوی Coolify با `COOLIFY_DEPLOY_URL` و `COOLIFY_TOKEN` (GitHub Secrets، Environment: `production`) صدا زده می‌شود.
2. تا سالم شدن دیپلوی صبر می‌کند (polling روی API Coolify یا `https://3evda.com/api/health/ready`).
3. smoke test روی دامنه‌ی واقعی: خانه با status ‏۲۰۰، health سالم، و نسخه‌ی گزارش‌شده برابر SHA همین commit (از `/api/health/live`).
4. **روش جایگزین:** اگر GitHub به سرور ایران دسترسی نداشته باشد، Auto Deploy خود Coolify روی `main` فعال می‌شود و این workflow فقط smoke test را اجرا می‌کند.

### ۲.۳ تعریف «انجام‌شده» (برای همه‌ی فازها)

- همه‌ی چک‌های اجباری سبزند و هیچ تستی skip یا غیرفعال نشده است.
- migrationها روی دیتابیس خالی و روی دیتابیس فاز قبل اجرا می‌شوند.
- `docker compose up` از صفر بالا می‌آید و همه‌ی سرویس‌ها healthy می‌شوند.
- رمز یا داده‌ی شخصی واقعی در کد وجود ندارد و `.env.example` به‌روز است.
- رابط کاربری جدید در هر دو زبان fa و en، در موبایل (۳۷۵px) و دسکتاپ، و با کیبورد قابل استفاده است.
- `README.md` و ران‌بوک‌ها به‌روز شده‌اند.
- دیپلوی روی Coolify سالم است و smoke test پاس شده است.

## ۳. فازها

### فاز ۰ — زیرساخت و CI/CD
**هدف:** اسکلت کامل که از PR تا Coolify کار می‌کند، قبل از نوشتن هر قابلیتی.
**برنامه‌ی تفصیلی:** `docs/superpowers/plans/2026-10-02-phase-0-foundation.md`

- Monorepo با `backend/` (Django 5.2 و پروژه‌ی `config`، تنظیمات از env، اپ `core`، health live/ready) و `frontend/` (Next.js 16، fa و en با next-intl، صفحه‌ی «به‌زودی» با توکن‌های رنگ برند)
- Dockerfileهای multi-stage با کاربر غیر root و آرگومان‌های میرور
- `docker-compose.yml` (gateway، web، api، worker، postgres، redis، storage) + `compose.dev.yml` + `.env.example`
- Caddy gateway با مسیریابی `/api`، `/django-admin`، `/static`، `/media` و `/`
- ADR انتخاب سرویس ذخیره‌سازی S3
- `ci.yml`، `deploy.yml`، Dependabot، قالب PR، Branch protection
- اولین دیپلوی روی Coolify با دامنه‌ی `3evda.com` و ران‌بوک `docs/runbooks/coolify.md`

**گیت:** همه‌ی jobهای CI سبز؛ E2E صفحه‌ی fa و en را از طریق gateway باز می‌کند، health ready برای Postgres و Redis و storage سالم است و overflow افقی ندارد؛ دیپلوی Coolify سالم است و smoke test پاس شده.

### فاز ۱ — احراز هویت ادمین، Media و اسکلت پنل
- **accounts:** فقط یک ادمین (invariant در دیتابیس)، دستور `bootstrap_admin`، ورود با session و CSRF، TOTP اجباری + کدهای بازیابی، django-axes برای قفل موقت، تغییر رمز (ابطال سایر sessionها)، خروج
- **audit:** ثبت ورود، خروج و تغییرات محتوا
- **media:** آپلود با اعتبارسنجی امضای MIME، حجم و ابعاد (ضد decompression bomb)، حذف EXIF و GPS، درج IPTC کپی‌رایت، تولید واریانت‌های WebP و AVIF در چند عرض و LQIP در worker، واترمارک قابل تنظیم، ویدیو (MP4/WebM + پوستر)، ارجاع‌ها و جلوگیری از حذف فایل در حال استفاده
- **پنل:** `/panel` شامل ورود، ثبت TOTP، چیدمان (سایدبار و هدر)، کتابخانه‌ی Media (آپلود گروهی کشیدنی، جست‌وجو، ویرایش alt دوزبانه)
- **contract:** schema OpenAPI و کلاینت orval، و فعال‌شدن job `contract`

**تست‌ها:** امکان‌ناپذیری ساخت ادمین دوم، شکست ورود بدون TOTP، قفل بعد از تلاش‌های ناموفق، عدم دسترسی بدون session به APIهای ادمین (تست ماتریسی روی همه‌ی endpointها)، رد فایل جعلی یا حجیم یا bomb، حذف EXIF، ساخت واریانت‌ها؛ E2E ورود و آپلود.
**گیت:** همه‌ی موارد بالا سبز؛ ثبت‌نام عمومی وجود ندارد؛ فایل اصلی هیچ‌وقت بدون URL امضاشده در دسترس نیست.

### فاز ۲ — سیستم طراحی، سایت عمومی و CMS
- **سیستم طراحی:** توکن‌های Tailwind از پالت تأییدشده، فونت‌های self-host (Vazirmatn، Fraunces، Inter)، کامپوننت‌های پایه (Button، Card، Dialog، Lightbox، Form controls) با تست دسترس‌پذیری
- **cms:** SiteSettings، منو، بخش‌های صفحه‌ی خانه (ترتیب و نمایش)، اسلایدهای هیرو، درباره من، خدمات، فرایند همکاری، مشتریان، نظرات، پشت صحنه، FAQ، شبکه‌های اجتماعی و تماس — همه دوزبانه
- **portfolio:** دسته‌ها، سبک (low-key/high-key)، پروژه/کیس‌استادی، تصاویر و ویدیوها، منتخب‌ها
- **pricing:** پکیج‌ها، ویژگی‌ها، قیمت یا «استعلام»، دسته‌ی خدمت
- **صفحات عمومی:** خانه، نمونه‌کارها (فیلتر، گرید justified، لایت‌باکس)، پروژه، خدمات، پکیج‌ها، درباره، تماس، و 404 و 500 دوزبانه
- **پنل:** CRUD همه‌ی موارد بالا با چیدمان drag، پیش‌نمایش، و revalidate هدفمند کش Next بعد از هر تغییر
- seed دیتای نمونه برای توسعه و E2E (بدون داده‌ی شخصی واقعی)

**تست‌ها:** API عمومی فقط محتوای منتشرشده و قابل‌نمایش برمی‌گرداند؛ ماتریس CRUD در E2E (ایجاد در پنل ← دیدن در سایت ← ویرایش ← حذف)؛ RTL و LTR؛ axe؛ Lighthouse ≥ ۹۰ (فعال‌شدن job `lighthouse`).
**گیت:** همه‌ی فیلدهای عمومی از پنل قابل ویرایش‌اند و ظاهر با پیش‌نمایش برند تأییدشده هم‌خوانی دارد.

### فاز ۳ — بلاگ و سئو
- **blog:** مقاله (یک رکورد برای هر زبان + `translation_group`)، دسته، برچسب، ویرایشگر TipTap با درج عکس از Media، پاک‌سازی allowlist با nh3، زمان مطالعه، وضعیت پیش‌نویس/زمان‌بندی/منتشرشده (انتشار زمان‌بندی‌شده با Celery beat)، پیش‌نمایش با لینک امضاشده، مقالات و پروژه‌های مرتبط
- **seo:** metadata برای هر صفحه، `hreflang` و canonical، Open Graph و تصویر OG خودکار، `sitemap.xml` (همه‌ی زبان‌ها)، `robots.txt`، RSS برای هر زبان، Schema (`LocalBusiness`/`Photographer`، `Article`، `BreadcrumbList`، `ImageObject`)، ریدایرکت ۳۰۱ خودکار هنگام تغییر slug
- **صفحات:** فهرست مجله (صفحه‌بندی، فیلتر دسته و برچسب)، صفحه‌ی مقاله، و صفحه‌ی دسته و برچسب

**تست‌ها:** پیش‌نویس هرگز عمومی یا در sitemap نیست؛ انتشار زمان‌بندی‌شده درست کار می‌کند؛ XSS در بدنه‌ی مقاله پاک می‌شود؛ ریدایرکت slug؛ snapshot متادیتا و Schema؛ E2E نوشتن و انتشار مقاله.
**گیت:** همه سبز؛ اعتبارسنجی sitemap و RSS؛ Lighthouse SEO ≥ ۹۵ روی صفحه‌ی مقاله.

### فاز ۴ — استعلام، ماشین‌حساب قیمت و پیش‌فاکتور
- **pricing:** QuoteRule (قیمت پایه، ضریب تعداد، استایلینگ، ویدیو، فوریت) و endpoint برآورد سمت سرور
- **inquiries:** فرم عمومی چندمرحله‌ای با برآورد زنده، پیوست اختیاری، honeypot، rate limit و محدودیت حجم؛ پنل شامل فهرست، فیلتر، جست‌وجو، جزئیات، یادداشت داخلی، تاریخچه‌ی وضعیت و خروجی CSV امن
- **proformas:** ساخت از صفر یا از استعلام، آیتم‌ها، تخفیف، مالیات، اعتبار، شرایط، شماره‌گذاری `3E-<سال شمسی>-<شماره>` (یکتا و تراکنشی)، PDF راست‌چین با WeasyPrint، لینک عمومی امضاشده با دکمه‌ی «تأیید» و ثبت زمان تأیید، وضعیت‌ها، و دکمه‌ی کپی لینک

**تست‌ها:** محاسبه‌ی قیمت (جدول حالت‌ها)، یکتایی شماره در درخواست‌های همزمان، PDF (متن فارسی قابل استخراج و جهت RTL)، لینک منقضی یا دست‌کاری‌شده، تأیید فقط یک‌بار، تزریق فرمول در CSV؛ E2E از ارسال استعلام تا تأیید پیش‌فاکتور.
**گیت:** همه سبز؛ استعلام ثبت‌شده بعد از reload در پنل دیده می‌شود.

### فاز ۵ — رزرو و تقویم شمسی
- **booking:** ساعات کاری هفتگی، روزهای بسته، ظرفیت روزانه، نوع جلسه (استودیو / در محل / ارسال محصول)؛ API زمان‌های آزاد؛ رزرو با وضعیت در انتظار ← تأییدشده ← انجام‌شده یا لغو؛ اتصال به پکیج، استعلام و پیش‌فاکتور
- **عمومی:** مسیر رزرو با تقویم شمسی (fa) یا میلادی (en)
- **پنل:** تقویم ماهانه و هفتگی، تأیید و رد، و جلوگیری از تداخل

**تست‌ها:** جلوگیری از رزرو دوگانه در درخواست‌های همزمان (قفل دیتابیس یا exclusion constraint)، تبدیل تاریخ شمسی و منطقه‌ی زمانی `Asia/Tehran`، روزهای بسته و ظرفیت؛ E2E رزرو و تأیید.
**گیت:** همه سبز.

### فاز ۶ — گالری مشتری و Proofing
- **galleries:** گالری با توکن، رمز اختیاری، انقضا، سقف انتخاب، و سطح دانلود؛ آپلود گروهی صدها عکس با صف پردازش و نوار پیشرفت؛ پیش‌نمایش واترمارک‌دار
- **مشتری (`/g/<token>`):** انتخاب، کامنت، درخواست ریتاچ، ارسال نهایی و قفل؛ دانلود تکی یا ZIP (ساخت در worker با لینک موقت)؛ دوزبانه و `noindex`
- **پنل:** وضعیت انتخاب‌ها، کپی نام فایل‌ها برای Lightroom، آپلود نسخه‌های نهایی، لاگ دانلود، فضای مصرفی، و آرشیو یا حذف خودکار پس از انقضا

**تست‌ها:** دسترسی با توکن اشتباه، منقضی یا بدون رمز؛ brute-force رمز (rate limit)؛ قفل بعد از ارسال؛ سقف انتخاب؛ ZIP درست و کامل؛ فایل اصلی بدون امضا در دسترس نیست؛ تست بار با ۵۰۰ عکس؛ E2E کامل مسیر مشتری.
**گیت:** همه سبز.

### فاز ۷ — سخت‌سازی و انتشار نهایی
- هدرهای امنیتی و CSP، بازبینی امنیتی کامل، تست نفوذ پایه (OWASP ASVS L1)
- بکاپ روزانه‌ی Postgres و فایل‌ها، نگهداری ۷ روزانه و ۴ هفتگی، اسکریپت و ران‌بوک ریستور، و **تمرین ریستور**
- لاگ ساخت‌یافته، correlation id، مانیتورینگ uptime، و هشدار پر شدن دیسک در داشبورد
- سیاست نگهداری داده (پاک یا ناشناس‌سازی استعلام‌های قدیمی و گالری‌های منقضی)
- ران‌بوک فارسی: دیپلوی، rollback، ریستور، تعویض رمز، و بازیابی دسترسی ادمین
- ورود محتوای واقعی و انتشار عمومی

**گیت:** همه‌ی CI سبز؛ ریستور موفق ثبت‌شده؛ Lighthouse ≥ ۹۰؛ چک‌لیست امنیتی تکمیل.
